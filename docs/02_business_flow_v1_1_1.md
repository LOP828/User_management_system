## 1. 文档信息

- 文档名称：业务流程与状态流转文档
- 版本：v1.1.1
- 依赖文档：MVP PRD v1.3
- 文档用途：描述用户从入库到最终状态的完整生命周期、每个阶段的状态流转规则、核心业务操作流程、以及页面间的跳转关系。供开发、测试、设计使用。

## 2. 全局状态总览

### 2.1 用户生命周期概览

一个用户从进入系统到最终，可能经历以下阶段：

```
用户到店付费
  → 入库建档（未配对池：新入库待处理）
    → 沟通补全资料（已沟通待推荐）
      → 红娘发起推荐（已推荐待选择）
        → 用户选中候选人（已选人待见面）
          → 首次见面
            ├── 双方愿意继续 → 创建配对卡（进入已配对池）
            │     ├── 推进顺利 → 成功申请 → 成功
            │     └── 关系终止 → 配对卡结束 → 回流未配对池
            └── 双方不继续 → 已见面未继续 → 回退到已沟通待推荐
```

用户在任意未配对状态下可进入"暂停中"，暂停解除后回到暂停前状态。

### 2.2 两个独立状态机

系统包含两个独立的状态机：

- **未配对池状态机**：管理用户从入库到首见成功前的全部状态
- **已配对池状态机**：管理配对卡从创建到成功/结束的全部阶段

用户在两个池子之间的流转通过明确的触发动作完成，不存在隐式跳转。

## 3. 未配对池状态机

### 3.1 状态列表

| 状态编号 | 状态名称 | 是否可推荐 | 是否可暂停 |
|---------|---------|-----------|-----------|
| S1 | 新入库待处理 | 否 | 是 |
| S2 | 已沟通待推荐 | 是（需资料完整） | 是 |
| S3 | 已推荐待选择 | 否（当轮进行中） | 是 |
| S4 | 已选人待见面 | 否 | 是 |
| S5 | 已见面未继续 | 否（需先处理失败） | 否 |
| S6 | 暂停中 | 否 | — |

### 3.2 状态流转规则

#### S1 → S2（新入库待处理 → 已沟通待推荐）

- 触发条件：红娘完成首次沟通，点击"标记已沟通"
- 前置检查：无
- 系统动作：更新用户主状态，写入操作日志
- 页面场景：用户详情页 → 点击状态变更按钮

#### S2 → S3（已沟通待推荐 → 已推荐待选择）

- 触发条件：红娘创建推荐批次并提交
- 前置检查：用户资料必须完整
- 系统动作：创建推荐批次 + 候选明细，更新用户主状态，写入操作日志
- 页面场景：用户详情页 → 点击"发起推荐" → 推荐批次创建页/弹窗 → 提交

#### S3 → S4（已推荐待选择 → 已选人待见面）

- 触发条件：红娘标记某候选人为"已选中"
- 前置检查：当前批次中至少有一个候选人
- 系统动作：更新候选明细的"是否被选中"字段，更新用户主状态，写入操作日志
- 页面场景：用户详情页 → 推荐记录区 → 点击候选人 → 标记选中

#### S4 → 创建配对卡（已选人待见面 → 进入已配对池）

- 触发条件：首次见面后，红娘确认双方愿意继续接触，点击"创建配对卡"
- 前置检查：被选中的候选人存在且状态正常
- 系统动作：
  1. 创建配对卡，主阶段设为"初期接触"
  2. 自动填入男方红娘、女方红娘、主操作红娘
  3. 更新候选明细的"是否见面"和"最终结果"
  4. 双方用户从未配对池移出
  5. 写入操作日志
- 页面场景：用户详情页 → 点击"创建配对卡" → 填写配对卡初始信息 → 提交 → 跳转到配对卡详情页

#### S4 → S5（已选人待见面 → 已见面未继续）

- 触发条件：首次见面后，红娘确认双方不继续
- 前置检查：无
- 系统动作：更新用户主状态，更新候选明细的"是否见面"和"最终结果"，写入操作日志
- 页面场景：用户详情页 → 点击"见面未继续" → 确认 → 用户进入"已见面未继续"

#### S5 → S2（已见面未继续 → 已沟通待推荐）

- 触发条件：红娘在"已见面未继续"状态下执行状态退出
- 前置检查：必须先提交一条包含 failure_reason_id 的未配对跟进记录
- 系统动作：
  1. 检查是否存在 scene = unmatched 且 failure_reason_id 已填写的跟进记录
  2. 用户主状态回到"已沟通待推荐"
  3. 自动挂上"待重新推荐"标签
  4. 写入操作日志
- 页面场景：先提交含 failure_reason_id 的失败跟进 → 再点击状态变更退出该状态 → 自动跳回用户详情页（状态已更新）

#### S3 → S2（已推荐待选择 → 已沟通待推荐）

- 触发条件：本轮推荐用户全部未选中，红娘关闭当前批次
- 前置检查：无
- 系统动作：更新用户主状态，自动挂上"待重新推荐"标签，写入操作日志
- 页面场景：用户详情页 → 推荐记录区 → 关闭当前批次

#### 任意状态（S1-S4） → S6（暂停中）

- 触发条件：红娘点击"暂停服务"
- 前置检查：用户不在 S5（已见面未继续需先处理完）
- 系统动作：
  1. 记录暂停前的主状态（用于恢复）
  2. 用户主状态切换为"暂停中"
  3. 必须填写暂停原因
  4. 写入操作日志
- 页面场景：用户详情页 → 点击"暂停服务" → 弹出暂停原因表单 → 提交

#### S6 → 暂停前状态（暂停解除）

- 触发条件：红娘点击"恢复服务"
- 前置检查：无
- 系统动作：用户主状态恢复为暂停前记录的状态，写入操作日志
- 页面场景：用户详情页 → 点击"恢复服务" → 确认 → 状态恢复

### 3.3 未配对池状态流转图（文本描述）

                    │  新入库待处理  │ S1
                    │    (T+0)     │
                    └──────┬───────┘

                           ▼

              │            │ 发起推荐（资料须完整）             │
              │            ▼                                │

              │        │       │                            │

```

## 4. 已配对池状态机

### 4.1 状态列表

| 阶段编号 | 阶段名称 | 可设风险标记 | 可发起成功申请 |
|---------|---------|------------|-------------|
| M1 | 初期接触 | 是 | 否 |
| M2 | 稳定联系 | 是 | 是 |
| M3 | 成功待审核 | 否 | — |
| M4 | 成功 | 否 | — |
| M5 | 结束 | 否 | — |

### 4.2 状态流转规则

#### M1 → M2（初期接触 → 稳定联系）

- 触发条件：主操作红娘根据回访情况判断关系已稳定，手动推进
- 前置检查：男方侧和女方侧各至少 1 条单方有效回访
- 系统动作：更新配对卡主阶段，写入操作日志
- 页面场景：配对卡详情页 → 点击"推进到稳定联系" → 确认

#### M2 → M3（稳定联系 → 成功待审核）

- 触发条件：主操作红娘发起成功申请
- 前置检查：
  1. 配对卡处于"稳定联系"阶段
  2. 男方侧和女方侧各至少 2 条单方有效回访
  3. 双方确认恋爱关系
  4. 稳定满 30 天
- 系统动作：
  1. 创建成功案例申请记录
  2. 配对卡主阶段切换为"成功待审核"
  3. 管理员待办 +1
  4. 写入操作日志
- 页面场景：配对卡详情页 → 点击"发起成功申请" → 填写申请信息 → 提交

#### M3 → M4（成功待审核 → 成功）

- 触发条件：管理员审核通过
- 前置检查：管理员角色权限
- 系统动作：
  1. 配对卡主阶段切换为"成功"
  2. 创建成功案例记录
  3. 以审核通过日为 T0，生成后续回访提醒（T0+30、T0+90、T0+180）
  4. 写入操作日志
- 页面场景：成功案例审批页 → 点击"通过" → 确认

#### M3 → M2（成功待审核 → 稳定联系，审核驳回）

- 触发条件：管理员驳回成功申请
- 前置检查：管理员角色权限
- 系统动作：配对卡主阶段回退为"稳定联系"，写入操作日志（含驳回原因）
- 页面场景：成功案例审批页 → 点击"驳回" → 填写驳回原因 → 确认

#### M1/M2 → M5（初期接触/稳定联系 → 结束）

- 触发条件：主操作红娘确认配对关系终止
- 前置检查：必须填写结束原因（男方、女方、红娘总结，至少填红娘总结）
- 系统动作：
  1. 配对卡主阶段切换为"结束"
  2. 双方用户自动回到未配对池，主状态设为"已沟通待推荐"
  3. 双方用户自动挂上"待重新推荐"标签
  4. 系统在双方用户档案写入情感经历摘要
  5. 写入操作日志
- 页面场景：配对卡详情页 → 点击"结束配对" → 弹出结束原因表单（男方原因、女方原因、红娘总结） → 提交 → 提示"双方用户已回流未配对池"

#### M4 → 失效处理（成功 → 已失效）

- 触发条件：成功案例后续回访发现关系已破裂
- 前置检查：配对卡当前为"成功"阶段
- 系统动作：
  1. 成功案例状态改为"已失效"
  2. 配对卡标记为"结束"
  3. 不自动回流未配对池（需红娘手动按新流程操作）
  4. 写入操作日志
- 页面场景：配对卡详情页 → 点击"标记失效" → 填写失效原因 → 提交

## 5. 核心业务流程

### 5.1 流程一：新用户入库建档

```
步骤  操作者    动作                        系统响应                   页面
───────────────────────────────────────────────────────────────────────
1    对接人员   用户到店，面谈沟通              —                       线下
2    红娘      打开系统，点击"新建用户"         跳转到新建用户表单         红娘首页 → 新建用户表单
3    红娘      填写最小必填字段                —                       新建用户表单
4    红娘      点击"保存"                    系统校验必填字段            新建用户表单
                                           创建用户记录
                                           自动设状态为"新入库待处理"
                                           自动写入入库时间
                                           写入操作日志
                                           跳转到用户详情页             → 用户详情页
5    红娘      继续补全完整资料（可选）          资料完整度标记更新          用户详情页
6    系统      T+1 若未推进                   生成普通提醒               —
```

### 5.2 流程二：推荐候选人

```
前置条件：用户状态为"已沟通待推荐"且资料完整

步骤  操作者    动作                        系统响应                   页面
───────────────────────────────────────────────────────────────────────
1    红娘      在用户详情页点击"发起推荐"      校验资料是否完整            用户详情页
                                           若不完整，提示先补全资料
                                           若完整，打开推荐批次创建页    → 推荐批次创建页
2    红娘      搜索/选择候选人                系统检查重复推荐：
                                           - 以前推荐过未见面 → 普通提示
                                           - 以前见面失败 → 高亮警告      推荐批次创建页
3    红娘      确认候选人列表，点击"提交"      创建推荐批次记录
                                           创建候选明细记录（每人一条）
                                           用户状态更新为"已推荐待选择"
                                           写入操作日志
                                           跳转回用户详情页             → 用户详情页
```

### 5.3 流程三：用户选中候选人

```
前置条件：用户状态为"已推荐待选择"，当前批次有候选人

步骤  操作者    动作                        系统响应                   页面
───────────────────────────────────────────────────────────────────────
1    红娘      在用户详情页查看推荐记录         展示当前批次候选人列表      用户详情页
2    红娘      点击某候选人 → "标记选中"       更新候选明细"是否被选中"
                                           用户状态更新为"已选人待见面"
                                           写入操作日志                用户详情页
```

### 5.4 流程四：首次见面 → 创建配对卡（见面成功）

```
前置条件：用户状态为"已选人待见面"

步骤  操作者    动作                        系统响应                   页面
───────────────────────────────────────────────────────────────────────
1    红娘      安排双方线下见面                —                       线下
2    红娘      见面后回到系统，点击"创建配对卡"  打开配对卡创建表单          用户详情页 → 配对卡创建表单
3    红娘      确认双方信息，点击"提交"         创建配对卡：
                                           - 主阶段 = 初期接触
                                           - 男方红娘 = 男方用户的负责人
                                           - 女方红娘 = 女方用户的负责人
                                           - 主操作红娘 = 当前红娘（创建者）
                                           - 风险等级 = 无风险
                                           更新候选明细（是否见面=是，最终结果=继续）
                                           双方用户从未配对池移出
                                           生成首次回访提醒（第7天）
                                           写入操作日志
                                           跳转到配对卡详情页           → 配对卡详情页
```

### 5.5 流程五：首次见面 → 不继续（见面失败）

```
前置条件：用户状态为"已选人待见面"

步骤  操作者    动作                        系统响应                   页面
───────────────────────────────────────────────────────────────────────
1    红娘      见面后确认双方不继续
              点击"见面不继续"               更新候选明细（是否见面=是，最终结果=不继续）
                                           用户状态更新为"已见面未继续"
                                           写入操作日志                用户详情页
2    红娘      在用户详情页点击"写跟进"         提交一条 scene=unmatched 的跟进记录
              选择 failure_reason_id          failure_reason_id 必填       用户详情页 → 跟进记录弹窗
3    红娘      再执行状态退出                   系统检查 failure_reason_id 跟进已存在
              （S5 → S2）                   用户状态回到"已沟通待推荐"
                                           自动挂上"待重新推荐"标签
                                           写入操作日志
                                           刷新用户详情页               → 用户详情页（状态已更新）
```

### 5.6 流程六：已配对回访

```
前置条件：配对卡处于"初期接触"或"稳定联系"

步骤  操作者        动作                     系统响应                   页面
───────────────────────────────────────────────────────────────────────
1    系统          回访提醒到期               分别发送提醒给男方红娘/女方红娘   —
2    男方红娘       收到提醒，打开配对卡详情页   展示配对卡信息                 手机端快速处理页
                                                                        或 配对卡详情页
3    男方红娘       点击"写跟进"              打开跟进记录表单
                                           scene 自动设为 matched
                                           match_card_id = 当前配对卡
                                           user_id = 男方用户ID         跟进记录表单
4    男方红娘       填写：                    —                            跟进记录表单
                  - 跟进内容
                  - 是否仍联系
                  - 风险情况
                  - next_remind_mode（manual/default）
                  - 若 manual，则填写 next_remind_at

                  "红娘综合判断"

## 9. 边界情况与异常处理

### 9.1 推荐时资料不完整

- 系统在"发起推荐"按钮点击时校验
- 若不完整，弹出提示"请先补全资料卡"，不允许进入推荐流程
- 提示可提供跳转到资料编辑区的快捷入口

### 9.2 重复推荐同一对候选人

- 系统在推荐批次创建页自动检查历史推荐
- 以前推荐过但未见面：显示普通提示（黄色），红娘可选择继续
- 以前见面过且失败：显示高亮警告（红色），红娘仍可选择继续，但管理员可在日志中查看

### 9.3 配对卡创建时双方状态冲突

- 若被选中的候选人已经被其他红娘创建了配对卡（已进入已配对池），系统应拦截
- 提示"该用户已在配对中，无法创建新配对卡"

### 9.4 用户同时存在多张配对卡

- 第一版规则：一个用户同一时间只能存在一张进行中的配对卡（主阶段为 M1-M3）
- 已结束（M5）和已成功（M4）的配对卡不占名额
- 系统在创建配对卡时校验

### 9.5 转移用户时有进行中的配对卡

- 转移审批通过后，系统自动更新配对卡上对应的红娘字段
- 例：男方用户从红娘A转移到红娘B，则配对卡的"男方红娘"自动从A更新为B
- 若该红娘同时是"主操作红娘"，主操作红娘字段不自动变更（需管理员手动调整）

### 9.6 暂停中用户被推荐为候选人

- 暂停中的用户不应出现在推荐候选人搜索结果中
- 系统在推荐批次创建页的候选人搜索中自动过滤暂停用户

### 9.7 成功审核驳回后再次申请

- 驳回后配对卡回到"稳定联系"，红娘可再次发起成功申请
- 不限制申请次数，但每次驳回原因均写入日志
