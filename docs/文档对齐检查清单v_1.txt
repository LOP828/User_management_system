文档对齐检查清单 v1
1. 使用说明
这份清单用于在正式开发前，检查以下文档之间是否存在冲突、遗漏或不一致：
PRD
状态流转
页面清单与页面字段清单
接口详细版
数据库表结构详细版
建议使用方式：
第一遍
只检查是否存在明显冲突。
第二遍
给每一项标记：
已对齐
部分对齐
未对齐
第三遍
把没有对齐的内容补回主文档。
2. 产品层对齐检查
2.1 产品定位是否一致
检查点：
PRD 中是否明确写明：这是配对跟进管理系统，而不是匹配算法系统
页面设计中是否出现偏向智能推荐平台的内容
接口中是否提前出现大量算法接口
数据库中是否过早引入复杂画像、向量、算法字段
目标：
所有文档都服务于“管理、跟进、提醒”这个核心。
2.2 MVP 范围是否一致
检查点：
PRD 中是否明确第一版不做复杂 BI
页面中是否已经出现复杂统计和报表页面
接口中是否出现大量分析报表接口
数据库中是否为了未来 BI 做了过度建模
目标：
第一版只做必要闭环，不做过度扩张。
2.3 角色权限是否一致
检查点：
红娘与管理员的权限边界是否在所有文档中一致
页面按钮是否按角色做了区分
接口是否定义了权限限制
数据库是否能记录操作者、审批者、负责人
重点确认：
红娘不能审批成功案例
红娘不能审批转移
管理员能强制改状态和负责人
操作日志只有管理员可看
3. 状态流转对齐检查
3.1 用户主状态是否统一
检查点：
以下用户主状态在所有文档中是否统一：
新入库待处理
已沟通待推荐
已推荐待选择
已选人待见面
已见面未继续
暂停中
重点检查：
页面筛选项是否多出状态
接口里状态名是否一致
数据库枚举是否完整
3.2 “待重新推荐”是否始终作为标签
检查点：
状态流转表中是否定义为标签
页面中是否作为标签而不是主状态
接口是否在 tags 中返回
数据库是否落在 customer_tags / customer_tag_relations
是否没有被混入 customer_profiles.current_status
3.3 未首见规则是否统一
检查点：
PRD 是否明确未首见用户走单独规则
状态流转里未首见是否属于提醒而不是状态
页面中是否有未首见延迟 / 未首见超时标签或提示
接口是否有对应提醒逻辑
数据库是否能存 current_timeout_type 和 current_timeout_reason_code
重点确认：
未首见是提醒逻辑，不是新的主状态。
3.4 已配对阶段是否统一
检查点：
以下配对卡阶段在所有文档中是否一致：
初期接触
稳定联系
暂停
成功待审核
成功
结束
重点检查：
页面下拉选项是否一致
接口 change-stage 是否一致
数据库枚举是否一致
3.5 风险到底是标签还是主状态
检查点：
PRD 是否收口为风险先做标签
状态流转表中是否没有“风险中”主状态
页面是否展示 risk_flag / risk_reason
接口是否使用风险字段而非改主阶段
数据库是否采用 risk_flag + risk_reason_code
3.6 成功流转是否完整
检查点：
是否先发起成功申请
是否进入成功待审核
是否由管理员审核
是否通过后进入成功
是否驳回后回到稳定联系
重点确认：
页面有发起申请按钮
接口有申请、通过、驳回
数据库有 success_applications 和 success_cases
状态流转表中有完整回退逻辑
4. 页面与状态对齐检查
4.1 页面按钮是否都有状态流转依据
检查方式：
对每个页面按钮问：这个按钮点下去，会让对象发生什么状态变化？
重点检查：
用户详情页按钮
发起推荐
暂停用户
恢复用户
写跟进
设置提醒
配对卡详情页按钮
新增回访
改阶段
发起成功申请
结束配对
暂停关系
如果某个按钮没有状态流转依据，说明它可能是拍脑袋加上的。
4.2 页面显示字段是否都能在数据库找到落点
检查方式：
对页面每个字段问：数据库里到底存在哪张表哪个字段？
例如：
当前状态 → customer_profiles.current_status
最近见面时间 → customer_profiles.last_meet_at
风险原因 → pair_cards.risk_reason_code
男方热度 → pair_cards.male_interest_score 或 pair_card_followups.male_interest_score
如果页面要显示但数据库没有位置，就是未对齐。
4.3 页面筛选项是否都能被接口支持
重点检查：
页面中的筛选条件，接口是否都支持对应 query 参数。
例如未配对池筛选项：
主状态
付费等级
负责人
超时原因
是否资料完整
是否待重新推荐
是否未首见超时
如果页面能筛，接口不能筛，就是未对齐。
4.4 手机端快速处理页是否符合“快速处理”目标
检查点：
是否默认只展示关键区
是否支持快速写跟进 / 标记已处理 / 改状态 / 设提醒
是否没有把整页做成 PC 详情页搬运版
5. 页面与接口对齐检查
5.1 每个页面动作是否都有接口承接
按页面逐一检查：
红娘首页
获取首页数据 → /dashboard/matchmaker
未配对池列表页
获取列表 → /users
查看详情 → /users/{id}
写跟进 → /users/{id}/followups
改状态 → /users/{id}/change-status
发起推荐 → /users/{id}/recommendation-batches
配对卡详情页
查看详情 → /pair-cards/{id}
新增回访 → /pair-cards/{id}/followups
改阶段 → /pair-cards/{id}/change-stage
发起成功申请 → /pair-cards/{id}/success-applications
结束配对 → /pair-cards/{id}/close
管理员页
审批转移 → /transfer-requests/{id}/approve
审批成功 → /success-applications/{id}/approve
如果某个页面动作没有对应接口，就是断层。
5.2 接口是否存在页面根本用不到的冗余内容
检查方式：
问：这个接口第一版页面真的会调用吗？
如果当前页面根本没有入口，也不服务 MVP 核心闭环，就先压后。
6. 接口与数据库对齐检查
6.1 每个接口写入的数据，数据库是否能承接
重点检查：
创建用户
是否能写入：
customer_profiles
operation_logs
reminder_tasks
发起推荐
是否能写入：
recommendation_batches
recommendation_candidates
用户状态/时间字段/日志
新增回访
是否能写入：
pair_card_followups
pair_cards 冗余字段
reminder_tasks
operation_logs
6.2 需要历史追踪的动作是否都有历史表
重点检查：
用户状态变化 → user_status_histories
配对卡阶段变化 → pair_card_status_histories
用户跟进 → user_followups
配对回访 → pair_card_followups
审计 → operation_logs
6.3 原因编码是否能统一对上原因库
重点检查：
暂停原因
失败原因
超时原因
风险原因
确认：
页面下拉项来自 dictionary_items
接口传 reason_code
数据库存 reason_code
没有页面中文、接口英文、数据库另一个编码的混乱情况
6.4 唯一约束和业务规则是否一致
重点检查：
同一用户同一时刻不能有两张未结束配对卡
同一批次候选不能重复
同一门店付费等级不能重名
同一账号只能有一个 staff_profile
7. 提醒逻辑对齐检查
7.1 提醒类型是否在三个层面一致
三个层面：
PRD / 业务规则
接口
数据库 reminder_tasks.reminder_type
重点检查：
first_meet_push
first_meet_delay
first_meet_timeout
followup_due
pause_revisit
success_revisit
manual
7.2 手动提醒“只覆盖本次”是否落到了接口和数据层
检查点：
PRD 里是否写明
接口说明里是否写明
数据库里是否有 manual_override
服务逻辑后续是否能恢复默认提醒规则
7.3 首页综合分逻辑是否至少有落点
检查点：
PRD 中综合分因子是否明确
页面需要展示排序结果
接口支持 sort_by
数据库有 priority_score 落点
8. 审批流对齐检查
8.1 转移审批链路是否闭环
检查：
红娘能发起申请
管理员能审批
审批通过后负责人改变
原负责人和新负责人收到通知
日志记录变更
页面有转移审批入口
数据库有 transfer_requests
8.2 成功审批链路是否闭环
检查：
红娘发起成功申请
配对卡进入待审核
管理员审批通过 / 驳回
通过后进入成功案例库
创建 30 / 90 / 180 天提醒
页面能看申请
数据库有 success_applications 和 success_cases
9. 日志与审计对齐检查
9.1 关键动作是否都定义了日志
重点动作包括：
创建用户
改用户状态
暂停 / 恢复用户
创建推荐批次
登记见面结果
创建配对卡
改配对卡阶段
新增配对回访
发起成功申请
审批成功
发起转移
审批转移
管理员强制改状态 / 负责人
9.2 日志是否只读
检查：
PRD 是否写了不可篡改
页面是否只提供查看
接口是否没有修改日志
数据库是否不需要日志更新场景
10. MVP 收敛检查
10.1 是否有不该进入第一版的内容混入
重点检查：
复杂画像向量
算法推荐
太重的统计报表
多门店联动
自动分配
复杂通知策略
用户端功能
10.2 第一版是否仍围绕 4 个闭环
检查第一版是否仍服务于这四条主链：
闭环1
用户入库 + 未配对池 + 超时提醒
闭环2
推荐批次 + 见面结果 + 回退
闭环3
已配对池 + 回访 + 风险 + 成功申请
闭环4
管理员审批 + 日志 + 通知
如果某份文档中的内容不服务这四个闭环，就先往后压。

12. 使用结论
这份清单的作用，不是生成新的文档，而是在开发前做最后一轮结构化检查，避免出现：
业务规则写了但页面没体现
页面有按钮但接口没定义
页面字段想显示但数据库没地方存
状态流转和审批逻辑彼此打架
第一版范围不知不觉膨胀
