## 3. 开发顺序与闭环划分

### 3.1 推荐开发顺序

按依赖关系从底层到上层：

```
阶段一：地基层
  闭环 1：项目骨架 + 数据库 + 认证
  闭环 2：配置管理（原因枚举 + 付费等级）

阶段二：核心实体
  闭环 3：用户档案 CRUD
  闭环 4：未配对池状态机

阶段三：推荐与配对
  闭环 5：推荐流程
  闭环 6：配对卡 CRUD + 状态机

阶段四：跟进与提醒
  闭环 7：跟进记录
  闭环 8：提醒系统 + Celery 定时任务

阶段五：审批流程
  闭环 9：成功案例申请与审批
  闭环 10：用户转移申请与审批

阶段六：聚合与展示
  闭环 11：首页聚合接口
  闭环 12：操作日志

阶段七：前端
  闭环 13：PC端核心页面
  闭环 14：小程序端

阶段八：联调与安全
  闭环 15：全链路联调
  闭环 16：安全审计
```

## 5. 每日开发收尾 SOP

每天开发结束前，花 10 分钟执行：

```
1. 今天完成了哪个闭环的哪些检查项？
   → 在检查清单中标记 ✅

2. 有没有发现代码和文档的偏差？
   → 如果是代码偏了 → 修代码
   → 如果是文档有遗漏 → 记录到文档待修订列表

3. 把今天写的核心 services.py 代码喂给 Claude：
   "以下是我今天写的 {模块名} 业务逻辑代码，
    请对照以下业务规则检查有没有遗漏或矛盾：
    {粘贴对应的 BR 规则}"

4. 如果今天涉及权限相关代码，额外做一次：
   "以下是我的 permissions.py 代码，
    请对照以下权限矩阵检查有没有越权风险：
    {粘贴对应的权限矩阵章节}"

5. git commit + push
```

## 6. 偏差处理规则

| 偏差类型 | 处理方式 |
|---------|---------|
| 代码实现和文档不一致 | 优先修改代码对齐文档。如果文档定义不合理，先改文档再改代码。 |
| 文档中未覆盖的边界情况 | 代码先实现合理的处理，同时补充到04业务规则文档中。 |
| 权限漏洞 | 立即修复，不留到后续闭环。 |
| 接口响应格式和文档不一致 | 修改代码对齐06API契约。如果文档格式不合理，先改文档。 |

**核心原则：文档是 single source of truth。代码对齐文档，不是文档对齐代码。**
